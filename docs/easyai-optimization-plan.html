EasyAI 框架优化方案 v2.0

统一注解驱动 · 新增意图识别 · 管道重构 · 生产级补强

一、优化目标与原则

核心目标

  1. 统一技术栈 — 彻底移除旧版场景处理器体系，全量统一到注解驱动 + 管道式引擎
  2. 闭环对话体验 — 新增意图识别阶段，用户无需指定 taskType，框架自动识别并路由
  3. 生产级可靠性 — 解决并发安全、LLM 工程化、可观测性、displayValue 等关键缺陷
  4. 开发者体验 — 一个注解声明一个任务，一套引擎跑所有场景，减少心智负担

设计原则

  • 内部表示与用户表示分层 — value 给系统用，displayValue 给用户看，rawValue 留痕
  • 每一步都可观测 — 管道每个阶段产出 metrics 和 trace
  • 失败可恢复 — LLM 失败重试、降级；状态持久化；并发安全
  • 渐进式重构 — 分阶段实施，每阶段可独立交付和验证

四、新增：意图识别阶段（第 0 阶段）

4.1 设计目标

用户说"帮我改一下订单"，框架自动识别为 ORDER_UPDATE 任务，无需调用方预先判断。同时支持：

  • 会话连续性 — 同一 sessionId 下已有进行中的任务，直接继续，不重复识别
  • 低置信度澄清 — 识别不确定时，列出可选任务让用户选择
  • 任务切换 — 用户明确说"算了，我要查物流"时，能切换到新任务
  • 闲聊/兜底 — 无法匹配任何任务时，返回通用回复或转人工

五、P0 优化（必须先做）

5.1 并发安全 — 乐观锁

问题

TaskStateManager 的 load-modify-save 不是原子操作，同一 taskId 并发请求会导致状态覆盖。

方案

  1. ai_task_state 表新增 version 字段（FieldState 已有 version，TaskState 也加）
  2. 更新时 UPDATE ... SET version = version + 1 WHERE task_id = ? AND version = ?
  3. 影响行数为 0 时，说明被并发修改，重新 load 后重试（最多 3 次）
  4. 重试仍失败，返回"操作过于频繁，请稍后重试"
// TaskStateManager.save() 伪代码
public boolean save(TaskState state) {
    int currentVersion = state.getVersion();
    state.setVersion(currentVersion + 1);
    int rows = mapper.updateWithVersion(state, currentVersion);
    if (rows == 0) {
        // 并发冲突，重新加载后合并重试
        TaskState latest = load(state.getTaskId());
        mergeState(latest, state);  // 字段级合并，后写的字段优先
        return saveWithRetry(latest, 2);  // 剩余重试次数
    }
    return true;
}

5.2 LLM 工程化补强

5.2.1 重试机制

  • 对超时、5xx、429（限流）自动重试，指数退避（1s → 2s → 4s），最多 3 次
  • 4xx（除 429）不重试，直接失败
  • 重试次数和退避策略可配置

5.2.2 降级策略

  • 配置主模型 + 备用模型列表（如主：Kimi，备：Doubao）
  • 主模型重试耗尽后自动切换备用模型
  • 所有模型都失败时，返回友好提示"AI 服务暂时不可用，请稍后重试"

5.2.3 解析鲁棒性

  • LLM 返回带 markdown 标记（```json ... ```）时，正则提取 JSON 部分
  • JSON 轻微格式错误（尾逗号、单引号、注释）时，用容错解析器修复
  • 解析失败时，将原始响应 + 错误信息回传给 LLM，要求"只返回合法 JSON"，重试 1 次
  • 仍失败则标记提取失败，返回用户友好提示

5.2.4 Token 计数与成本

  • 每次 LLM 调用记录 prompt_tokens / completion_tokens / total_tokens
  • 按 taskType / 模型 / 租户维度聚合成本
  • 暴露 Metrics：easyai_llm_tokens_total、easyai_llm_cost_total

5.3 displayValue 分层

问题

枚举/业务字段的内部值（1、US、123）直接回显给用户，用户无法理解。

方案

  1. FieldState 新增 displayValue 字段
  2. ValidationResult 新增 displayValue 参数，校验器匹配成功时填充
  3. EnumValidator 匹配到 option 后，displayValue = option.getLabel()
  4. 业务校验器（CountryExistValidator 等）查询后，displayValue = 国家名称
  5. DefaultResponseBuilder.formatValue() 优先级：displayValue → rawValue → value
// EnumValidator 匹配成功时
OptionDefinition matched = match(element, options);
transformed.add(matched.getValue());
labels.add(matched.getLabel());  // 收集展示值

String displayValue = isList ? String.join("、", labels) : labels.get(0);
return ValidationResult.success(rawValue, value, displayValue, null);

// ResponseBuilder 回显
private String formatValue(FieldState fs) {
    if (fs.getDisplayValue() != null) return fs.getDisplayValue();
    if (fs.getRawValue() != null) return String.valueOf(fs.getRawValue());
    if (fs.getValue() != null) return String.valueOf(fs.getValue());
    return null;
}

效果：用户看到"报关方式: 单独报关"而非"1"，"国家: 美国"而非"US"，"收货渠道: DHL特快"而非"123"。

6.2 Token 预算与对话历史管理

问题

对话历史一直往 prompt 里塞，多轮后超 LLM 上下文窗口，直接报错。

方案

  1. 预算配置 — 每个任务配置 maxTokens（默认 4096），预留 20% 给 completion
  2. 历史裁剪 — 构建 prompt 时，从最近消息往前累加，超预算时裁剪最早的消息
  3. 摘要压缩 — 裁剪前，用 LLM 将被裁剪的历史压缩为一段摘要（"用户之前提供了客户单号 A、B，国家为美国"），放入 system prompt
  4. 字段状态优先 — TaskState 中已收集的字段值始终保留（体积小、信息密度高），只裁剪原始对话消息
// Prompt 构建时的预算控制
public String buildPrompt(TaskState state, List<ChatMessage> history, int maxTokens) {
    int reserved = (int)(maxTokens * 0.2);  // 预留 completion
    int budget = maxTokens - reserved;

    // 1. 始终包含系统提示 + 字段定义 + 当前待收集字段
    String systemPart = buildSystemPrompt(state);
    budget -= countTokens(systemPart);

    // 2. 从最近的历史往前加，超预算时裁剪并摘要
    List<ChatMessage> fitted = new ArrayList<>();
    for (int i = history.size() - 1; i >= 0; i--) {
        int tokens = countTokens(history.get(i));
        if (budget - tokens < 0) {
            // 裁剪 0..i 的历史，压缩为摘要
            String summary = summarize(history.subList(0, i + 1));
            fitted.add(0, new SystemMessage("历史摘要: " + summary));
            break;
        }
        fitted.add(0, history.get(i));
        budget -= tokens;
    }
    return systemPart + serialize(fitted);
}

七、P2 优化（体验与安全）

7.1 对话生命周期管理

能力设计
最大轮次限制 每个任务配置 maxTurns（默认 10），超过后返回"已达到最大对话轮次，请重新发起"并标记 FAILED
任务超时 配置 timeoutMinutes（默认 30），超时后状态标记 EXPIRED，用户回来时提示"会话已超时，请重新开始"
取消意图识别 意图识别阶段检测到"算了/不弄了/取消"等表达，主动将任务标记 CANCELLED，返回"好的，已取消"
恢复引导 用户隔一段时间回来继续未完成任务时，首条回复包含"我们上次聊到XX，还需要提供YY"的上下文回顾
字段修改 用户说"把报关方式改成买单报关"时，框架识别为对已收集字段的修改，重置该字段状态为 PENDING 并重新提取校验，其他字段保持不变

7.2 Prompt 注入防护

  1. 角色隔离 — 使用 LLM API 的 messages 结构（system / user / assistant），绝不将用户输入拼入 system prompt
  2. 输入长度限制 — 用户消息超过 maxInputLength（默认 2000 字符）时截断并提示
  3. 注入模式检测 — 正则检测"忽略以上指令/ignore previous/system:"等典型注入模式，命中时标记并降级处理（只做参数提取，不执行任何指令类内容）
  4. 输出白名单 — 提取结果只接受预定义字段，LLM 输出中出现未定义字段时忽略

八、P3 优化（锦上添花）

8.1 流式响应（SSE）

  • AiChatService.chatStream() 返回 Flux<ChatChunk>
  • LLM 支持流式输出时，token 级推送给前端
  • 提取/校验阶段不流式（需要完整结果），只在最终回复阶段流式
  • 前端打字机效果，降低等待焦虑

8.2 配置热更新

  • 注解配置是静态的（重启生效），新增 DB 配置覆盖层
  • ai_task_config_record 表存储 JSON 配置，优先级高于注解
  • 运营人员通过管理后台修改配置，发布新版本，新任务自动使用最新版
  • 进行中的任务绑定旧版本，不受影响（版本绑定机制已存在）
