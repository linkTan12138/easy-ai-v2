1. 目标与设计原则

1.1 改造目标

  1. 声明内聚：字段的提取规则（说明 / 示例 / 规则）、校验规则、枚举、映射全部以注解形式标注在实体类字段上，与业务代码同源、同库、同版本。
  2. 编译期可查：注解参数（正则、长度、枚举、校验类引用）由编译器校验，杜绝 DB JSON 手写导致的脏配置与运行时才发现的问题。
  3. 校验职责分层：
    • 框架层只保留与业务无关的通用校验：非空、正则、长度、数值区间、枚举映射、确认语义。
    • 客户层承载高定制化校验（存在性、权限、跨字段、依赖外部系统等）：客户实现一个校验类，注解用 Class 参数引用，即插即用。
  4. 引擎零改动：复用现有 AiTaskEngine 全部流水线能力，仅新增一个配置源实现（注解 → AiTaskConfig 的适配器）。
  5. 平滑过渡：注解模式与数据库模式并存，通过 easy-ai.task-engine.config-source 切换，可灰度、可回退。

1.2 设计原则

  • 配置模型不变：引擎内部仍然消费 AiTaskConfig / FieldDefinition / ValidationConfig ... 模型，注解只是"新的声明语法"，不引入第二套引擎。
  • 默认值对齐：注解缺省值 = 现有配置模型缺省值（如 required=false、allowEmpty=false、onFail=RETRY），保证行为一致。
  • 通用优先，定制后置：同一字段允许多个校验注解，执行顺序 = 声明顺序（通用在前、定制在后），定制校验失败也走现有 RETRY/BLOCK 语义。
  • 最小侵入：不要求客户改引擎、不要求改现有内置校验器接口；新增的注解包独立成 domain.annotation 子包。
  • 失败要快：启动期扫描即做配置自检（重复字段代码、校验类不存在、非法正则等），配置错误直接阻断启动而非运行期才发现。

2. 方案总览

双模配置架构：注解模式与数据库模式并存，引擎共用
一句话概括：新增「注解扫描 → 元数据模型 → AiTaskConfig」的适配链路，把它作为 AiTaskConfigService 的第二个实现接入；校验器侧统一走现有 ValidatorRegistry，通用校验由注解参数直接生成，定制校验由注解的 Class 参数解析为校验器实例并注册。

3. 注解集设计

3.1 注解总览

注解作用域作用对应配置模型
@AiTask类声明一个任务场景（taskType / name / description / action / completion）AiTaskConfig
@AiField字段字段基础元信息（code / name / type / required / order / sensitive）FieldDefinition
@AiExtract字段提取规则：说明 / 示例 / 规则 / 允许为空ExtractionConfig
@AiPremise字段前置条件（单条件或条件组）PremiseConfig
@AiOptions字段枚举选项（label ↔ value）OptionDefinition[]
@AiNotBlank @AiRegex @AiLength @AiRange @AiEnum @AiConfirm字段通用校验（框架内置）ValidatorDefinition[]
@AiValid（可重复）字段定制校验：以 Class 引用客户校验类，可带参数ValidatorDefinition[]
@AiNormalize字段标准化：以 Class 或 type 引用标准化器NormalizationConfig
@AiMapping（可重复）字段映射规则（target + source 表达式）MappingRule[]

3.2 类级注解 @AiTask

@AiTask 属性与默认值（对应 AiTaskConfig）
@Target(TYPE) @Retention(RUNTIME)
public @interface AiTask {
    String taskType();                // 任务类型，如 "ORDER_UPDATE"（必填，唯一）
    String name() default "";         // 场景名称，缺省取类名
    String description() default "";  // 场景描述（用于意图匹配提示）
    String actionType() default "";   // 主动作类型，如 "UPDATE_ORDER"
    String[] postActions() default {};// 后置动作类型，如 {"LOG"}
    int version() default 1;          // 配置版本（注解模式默认 1）
    // completion 聚合：required / optional 直接取自字段注解，无需重复声明；
    // 若需额外控制，可加：String[] requiredFields() default {}; String[] optionalFields() default {};
}

3.3 字段级基础注解 @AiField

@AiField 属性（对应 FieldDefinition 基础字段）
@Target(FIELD) @Retention(RUNTIME)
public @interface AiField {
    String code() default "";        // 字段代码，缺省取 Java 字段名（驼峰原样）
    String name() default "";        // 中文名称，缺省取字段名
    FieldType type() default STRING; // 框架字段类型；缺省由 Java 类型自动推断：
                                     //   String→STRING, Integer→INTEGER, Long→LONG,
                                     //   BigDecimal→DECIMAL, Boolean→BOOLEAN,
                                     //   List<String>→STRING_LIST, List<Integer>→INTEGER_LIST ...
    boolean required() default false;
    int order() default Integer.MAX_VALUE;  // 收集顺序
    boolean sensitive() default false;      // 敏感字段（脱敏）
}
type 自动推断规则由 TypeInferrer 组件负责，支持 @AiField(type = ...) 手动覆盖。类型推断是注解模式优于 DB JSON 的体验点之一——少写一个字段。

3.4 提取规则注解 @AiExtract（对应 ExtractionConfig）

@AiExtract 属性（说明 / 示例 / 规则 直接进 Prompt）
@Target(FIELD) @Retention(RUNTIME)
public @interface AiExtract {
    String description() default "";   // 字段含义说明（Prompt）
    String[] examples() default {};    // 示例值（Prompt），如 {"美国","加拿大"}
    String[] rules() default {};       // 提取规则（Prompt），如 {"返回字符串数组"}
    boolean allowEmpty() default false;
    // 进阶（可选 v1.1）：Class<? extends ExtractStrategy> strategy() default DefaultExtractStrategy.class;
}

3.5 前置条件 / 枚举 / 标准化 / 映射注解

@AiPremise / @AiOptions / @AiNormalize / @AiMapping 设计
@Target(FIELD) @Retention(RUNTIME)
public @interface AiPremise {
    String field();                 // 依赖的字段代码
    String op() default "exists";   // exists | notExists | eq | neq | in
    String value() default "";      // eq/neq 时的期望值
    String[] values() default {};   // in 时的期望值集合
    // 复杂条件树（AND/OR）可重复使用 @AiPremises({@AiPremise...}) + operator
}

@Target(FIELD) @Retention(RUNTIME)
public @interface AiOptions {
    AiOption[] value();
}
public @interface AiOption { String label(); String value(); }  // value 以字符串承载，扫描时按字段类型转换

@Target(FIELD) @Retention(RUNTIME)
public @interface AiNormalize {
    Class<? extends FieldNormalizer> by() default DefaultNormalizer.class; // 客户标准化器
    String type() default "";   // 或按现有 type 引用（兼容存量）
    String[] params() default {};  // k=v 形式的参数
}

@Target(FIELD) @Retention(RUNTIME) @Repeatable(AiMappings.class)
public @interface AiMapping {
    String target();            // 目标参数路径，如 "receiveChannelId"
    String source() default "$value";  // $value / $rawValue / $data.xxx / 字面量
}
映射规则是可选的：未标注 @AiMapping 的字段，扫描器生成默认映射 target = 字段代码, source = $value，与 demo 中大多数字段的写法一致。

3.6 使用示例（改造后的实体类形态）

UpdateOrderDto 注解化示意（含提取规则、通用校验、定制校验）
@AiTask(taskType = "ORDER_UPDATE", name = "修改订单",
        description = "收集修改订单所需字段，确认后执行修改",
        actionType = "UPDATE_ORDER", postActions = {"LOG"})
public class UpdateOrderDto {

    @AiField(name = "客户单号", type = STRING_LIST, required = true, order = 1)
    @AiExtract(description = "需要修改订单的客户单号，只提取涉及修改的单号",
               examples = {"test1123,JT1241241,5323112-"},
               rules = {"返回字符串数组，元素间用逗号分隔", "忽略不涉及修改订单的单号"})
    @AiNotBlank(message = "客户单号不能为空")
    @AiValid(by = CustomerExistValidator.class)            // ★ 定制校验：客户自实现
    private List<String> customerNos;

    @AiField(name = "收货渠道", order = 2)
    @AiExtract(description = "渠道名称一般以始发地、承运商、专线目的国等要素组合，常以“价”结尾",
               examples = {"U009-HKUPS红单5000价", "D011-香港DHL特快5000"},
               allowEmpty = true)
    @AiValid(by = ChannelExistValidator.class, params = {"channelType=receive"})
    @AiMapping(target = "receiveChannelId", source = "$data.id")
    @AiMapping(target = "receiveChannelName", source = "$value")
    private String receiveChannelName;

    @AiField(name = "报关方式", type = INTEGER, order = 5)
    @AiOptions({@AiOption(label = "其他", value = "0"),
                @AiOption(label = "单独报关", value = "1"),
                @AiOption(label = "买单报关", value = "3")})
    @AiEnum()                                              // 通用校验：label→value 映射
    private Integer declareType;

    @AiField(name = "确认信息", required = true, order = 8)
    @AiPremise(field = "customerNos", op = "exists")
    @AiOptions({@AiOption(label = "确认", value = "1"), @AiOption(label = "其他", value = "0")})
    @AiConfirm(confirmValue = "1")                         // 通用校验：确认语义 + confirmed 标志
    @AiMapping(target = "confirmed", source = "$data.confirmed")
    private String isConfirm;
}
对照可见：原来 200+ 行的 DB JSON（ORDER_UPDATE 配置）压缩为几十行实体类注解，且字段声明、提取规则、校验、枚举、映射全部内聚在同一个字段上。客户新增一个定制校验 = 写一个校验类 + 加一行 @AiValid(by = Xxx.class)，不再需要动数据库。

4. 自定义校验体系

4.1 校验类形态（客户视角）

为降低客户心智负担，在现有 FieldValidator（type + params 风格，面向配置驱动）之上，提供更贴近注解语义的子接口，两者并存：

自定义校验接口（新，注解友好）与现有 FieldValidator 的关系
// 方案 A（推荐）：注解专用接口 —— 参数为强类型注解信息 + 上下文
public interface AnnotationValidator extends FieldValidator {
    // type() 由框架根据 Class 自动生成（如类简单名），无需手写
    // validate() 中可直接通过 FieldContext 拿：tenantId / userDetails / 其他字段值 / 配置参数
}

// 方案 B（兼容存量）：直接实现现有 FieldValidator + @AiValidator("TYPE")
// 适合已有校验器平滑迁移，@AiValid 提供 type 属性引用：
//   @AiValid(type = "CUSTOMER_EXIST")

// 校验器实例化规则（优先级从高到低）：
// ① 从 Spring 容器按 Class 取 Bean（校验类标注 @Component 时，可注入 Mapper/Service）
// ② 容器中无此 Bean → 框架反射实例化（无参构造），每次调用复用单例（缓存于 Map<Class, FieldValidator>）
// ③ 实例化失败 → 启动自检阶段直接报错，阻断启动（快速失败）

4.2 @AiValid 注解设计（核心诉求）

@AiValid —— 以 Class 为参数引用客户校验类，可重复，可带参数
@Target(FIELD) @Retention(RUNTIME) @Repeatable(AiValids.class)
public @interface AiValid {
    Class<? extends FieldValidator> by();   // ★ 客户自定义校验类（必填）
    String[] params() default {};           // 参数，k=v 形式，如 {"channelType=receive"}
    String message() default "";            // 失败提示语（可选，覆盖校验类默认文案）
    String onFail() default "RETRY";        // 失败策略：RETRY 追问 | BLOCK 终止任务
    int order() default Integer.MAX_VALUE;  // 管道内顺序（默认按声明顺序）
}
为什么用 Class 而不是 type 字符串：①编译期即可校验类是否存在、是否实现正确接口；②IDE 可跳转、可重构；③类即文档，客户的校验逻辑和声明在同一个仓库；④框架侧自动用 Class.getName()（或简单名）作为 ValidatorRegistry 的 type 键，无需人工命名冲突。

4.3 校验上下文与能力边界（客户校验类能做什么）

能力获取方式典型用途
当前字段值与定义FieldContext.fieldCode / fieldDefinition读取字段元信息（如 options）
租户 / 登录人FieldContext.taskContext.get("tenantId" / "userDetails")租户隔离、数据权限
其他字段已收集值FieldContext.fieldStates（Map<code, FieldState>）跨字段校验（如 A 依赖 B 的取值）
业务数据查询校验类声明 @Component，注入 Mapper/Service存在性、唯一性、权限、状态机校验
外部系统 / RPC同上，注入 Feign/HTTP 客户端风控、库存、黑名单等
附加数据回传ValidationResult.success(raw, value, data)校验通过时带回 id/名称等，供 @AiMapping 使用
值转换返回 ValidationResult.success(..., value) 管道接力标准化、格式统一（下流继续校验）
职责边界：客户校验类只做"判定 + 附加数据"，不做对话编排、不做状态修改；失败消息由框架按 RETRY/BLOCK 语义自动转换为追问文案。这与现有 validField() 的返回约定（CollectFieldValidVo）语义对齐，但声明位置从处理器 Java 代码 / DB JSON 移到字段注解。

4.4 校验管道执行语义

字段校验管道（通用注解在前 → 定制校验在后，失败即短路）
以 customerNos 字段为例，注解声明顺序即执行顺序：
  @AiNotBlank(message="客户单号不能为空")          → NOT_EMPTY 内置校验器
  @AiValid(by = CustomerExistValidator.class)     → 客户校验类（注册为 type=CustomerExistValidator）

rawValue ──▶ NOT_EMPTY ──▶ CustomerExistValidator ──▶ 标准值 + data{customerNo...}
                │                   │
                └─ 失败：INVALID + 追问文案；通过则进入下一个

规则：
· 同一字段多个校验按 @Order / 声明顺序执行；前一个的 value/data 输出作为后一个输入（管道）。
· 任一失败 → FieldState=INVALID，记 errorCode/errorMessage，遵循 onFail（默认 RETRY）。
· 通用校验注解与 @AiValid 可混合排列（通用放前面通常更合理，避免无谓的昂贵定制校验）。

5. 运行时机制（扫描 → 注册 → 引擎）

5.1 启动期组件

组件职责实现要点
AnnotationConfigScanner扫描 @AiTask 注解类，读取全部字段注解，构建元数据模型复用 Spring ClassPathScanningCandidateComponentProvider 或 ApplicationContext.getBeansWithAnnotation(AiTask.class)；支持配置扫描包路径
AnnotationMetaModel注解 → AiTaskConfig 的中间表示（AiTaskMeta / FieldMeta / ValidMeta / ExtractMeta / OptionMeta / MappingMeta）与引擎配置模型解耦，便于后续支持更多注解/校验器演进
AnnotationConfigBuilder元数据模型 → 完整 AiTaskConfig（含类型推断、默认映射、默认 completion 聚合）唯一"翻译器"，产出结果与 DB JSON 解析结果结构一致
AnnotationConfigValidator启动自检：taskType 重复、字段 code 重复、校验类不存在/未实现接口、非法正则、params 键值格式、options 值类型转换失败等任何一项不过 → 抛 ConfigValidationException 阻断启动
AnnotationValidatorRegistrar遍历所有 @AiValid 引用的 Class，实例化/取 Bean，按 Class 名注册进现有 ValidatorRegistry与现有 ValidatorRegistrar 并存；同一 Class 去重注册
AnnotationAiTaskConfigService实现 AiTaskConfigService：get() / getLatestPublished() / 版本 / 生命周期方法注解模式版本固定（@AiTask.version），生命周期方法（saveDraft/publish/disable）抛 UnsupportedOperation 或仅支持 list/get

5.2 装配开关与优先级

application.yml 配置（复用现有 AiTaskProperties，新增 config-source 取值）
easy-ai:
  task-engine:
    enabled: true
    config-source: annotation   # ★ database（默认/现状）| annotation（新） | json（预留）
    scan-packages: com.your.biz.dto   # 注解模式必填：@AiTask 实体所在包（可逗号分隔多个）
    # 优先级说明：同一 taskType 不允许双源共存（启动自检拦截）；
    # 迁移期可先全部切换 annotation，或按 taskType 前缀分流（见第 8 节灰度）

5.3 运行时行为对齐

  • 版本语义：注解模式下 version 取自 @AiTask.version（默认 1）。任务绑定版本逻辑不变；若需"配置热更新"，注解模式依赖发布新代码（符合"代码即配置"的定位），动态场景仍可用数据库模式。
  • 缓存：注解配置在启动期构建一次放入不可变缓存（ConcurrentHashMap），运行期零 IO，天然不可变。
  • 敏感字段脱敏：@AiField(sensitive=true) 映射到 FieldDefinition.sensitive，沿用现有会话记录脱敏逻辑。
  • 完成判定：required/optional 由 @AiField(required=true) 聚合生成 CompletionConfig，行为与现状一致（required 字段全 VALID + 无 INVALID 即完成）。
  • 意图匹配（旧链路）：注解模式的场景描述同样可提供给旧链路 matchScenario（如需并存，由适配层把注解配置同步进 TbTaskFieldTemplate 的镜像表或直接改造 matchScenario 读取 config 源）。

6. 框架内置通用校验清单

框架只保留与具体业务无关的通用校验，以注解形式直接声明在字段上：

注解属性映射内置校验器说明
@AiNotBlankmessageNOT_EMPTY非空（空串/空集合视为缺失）
@AiRegexpattern, messageREGEX正则匹配，支持集合逐元素校验
@AiLengthmin, max, messageSTRING_LENGTH长度区间（含边界）
@AiRangemin, max, messageNUMBER_RANGE数值区间
@AiEnummessageENUM配合 @AiOptions 做 label→value 映射
@AiConfirmconfirmValue, messageCONFIRM确认语义，data.confirmed 供映射
取舍原则：是否进入框架内置，看它是否"零业务假设"。正则、长度、区间、非空、枚举、确认都是纯格式/语义层校验；凡是需要"查某个表/调某个服务/判断某个业务状态"的，一律走 @AiValid(by = 客户类)。

7. 框架业务校验器去留

现状（框架内置）处置去向
NOT_EMPTY / REGEX / STRING_LENGTH / NUMBER_RANGE / ENUM / CONFIRM保留框架内置通用校验器（不动）
CUSTOMER_EXIST / CUSTOMER_PERMISSION下沉迁移移入 easy-ai-demo（示例客户实现），框架侧标记 @Deprecated 保留一版兼容期后删除；客户业务侧自行实现同名逻辑并通过 @AiValid(by = ...) 引用
CHANNEL_EXIST / COUNTRY_EXIST / WAYBILL_EDITABLE下沉迁移同上；SPI 接口（CustomerLookupService 等）保留在框架作为"可选能力"，但不再内置默认业务校验器
BusinessValidatorSupport / ValueUtils保留作为校验工具基类/工具类留在框架（与业务无关）
兼容策略：v1 版本内置业务校验器仅标记 @Deprecated 并继续工作（存量 DB 配置仍可解析）；v2 移除。同时发布迁移小工具/文档，将存量配置中的 {"type":"CUSTOMER_EXIST"} 一键改写为 @AiValid(by=CustomerExistValidator.class) 形态。

8. 兼容与灰度策略

8.1 三种 config-source 并存

模式适用场景配置管理方式
database（默认）存量部署、运营需动态调整配置现有 /easyai/engine/config/* 管理接口 + 版本化
annotation（新增）研发主导、配置与代码同源的业务改实体类注解 → 发版
json（预留）轻量部署、不想用数据库classpath:ai-task-configs/*.json

8.2 灰度路径（推荐）

  1. 影子期：新业务直接用 annotation 模式新建 taskType；存量 taskType 仍走 database。启动自检保证同一 taskType 不双源。
  2. 迁移期：对存量 taskType，用「配置导出 → 实体类骨架生成」工具生成注解实体，人工核对提取规则/校验/枚举后，切换 config-source（可按 taskType 白名单分流，如 annotation-task-types: ORDER_UPDATE）。
  3. 回退：切换后任何问题，将 taskType 从白名单移除即回退到数据库模式，在途任务不受影响（绑定版本逻辑不变）。
  4. 收敛期：全部迁移完成后移除 database 支持（可选），删表保留迁移脚本。

8.3 注解模式下 AiTaskConfigService 接口的处理

  • get / getLatestPublished / getLatestVersion / list：完整支持（基于启动期构建的内存注册表）。
  • saveDraft / publish / disable：注解模式抛 UnsupportedOperationException（配置随代码走，不由运行时管理）；管理端 Controller 在该模式下自动隐藏配置 CRUD 入口。

9. 迁移路径（DB → 注解）

9.1 手工迁移步骤（单场景）

  1. 新建（或改造）场景 DTO：类上加 @AiTask，字段加 @AiField/@AiExtract/.../@AiValid，内容逐项对照原 DB JSON 的 FieldDefinition。
  2. 业务定制校验器：把框架内置业务校验器（或旧 validField switch 分支）改写为客户校验类，字段上 @AiValid(by = ...) 引用。
  3. 配置 config-source: annotation + scan-packages，启动验证（自检通过 + 控制台打印各 taskType 已注册配置）。
  4. 用「对话冒烟用例」回归：每条字段的提取 → 校验（含失败分支）→ 映射 → 动作。
  5. 切换分流 → 观察 → 确认后纳入白名单。

9.2 可提供的配套工具（建议）

  • 配置导出器：读 ai_task_config 指定 taskType 的 JSON → 生成注解实体类骨架（含提取规则/枚举/映射，定制校验生成 TODO 占位类）。
  • 配置对比器：注解模式构建的 AiTaskConfig 与数据库最新 PUBLISHED 配置做字段级 diff，保障迁移零差异。
  • 文档生成器：注解扫描结果 → Markdown 配置手册（每个 taskType 的字段、校验、Prompt 片段），供产品/运营查阅。

10. 实施计划

Phase 1 · 注解定义与元数据模型（约 3~5 人日）
  • 新增 domain.annotation 包：@AiTask / @AiField / @AiExtract / @AiPremise / @AiOptions / @AiNotBlank / @AiRegex / @AiLength / @AiRange / @AiEnum / @AiConfirm / @AiValid / @AiNormalize / @AiMapping 及可重复容器注解。

  • 验收：注解可被反射完整读取；类型推断正确；可重复注解容器工作正常。

  • 验收：对 demo 的 ORDER_UPDATE 编写注解版 DTO，构建出的 AiTaskConfig 与 DB JSON 版本逐字段 diff 一致；非法注解（重复 code / 坏校验类）能阻断启动并给出明确报错。
Phase 3 · AnnotationAiTaskConfigService + 装配开关（约 2~3 人日）

  • 管理端 Controller 在注解模式下隐藏配置 CRUD。
  • 验收：AiTaskEngineController /chat 用注解配置跑通完整"提取→校验→映射→动作"链路；任务绑定版本、状态持久化、失败重试与 DB 模式行为一致。

11. 风险与对策

风险影响对策
注解模式失去"运行时改配置"能力运营侧动态调整受限双模并存：动态调整场景保留 database；注解模式面向研发主导场景；必要时提供「注解 → DB 配置同步器」
存量业务量大，迁移成本高推广受阻提供导出器/对比器；白名单灰度；迁移期双模共存可随时回退
校验类注入 Spring 依赖失败（客户忘记加 @Component）运行期 NPE / 校验不生效启动自检：扫描时即校验 Class 可实例化；取 Bean 失败自动回退反射实例化并打印告警；文档明确最佳实践
注解膨胀，字段注解过多影响可读性实体类变重注解语义化拆分（职责单一）；必要时支持「元注解组合」（客户自定义复合注解）；示例文档提供最佳排版
同一 taskType 双源误配行为不确定启动自检强制互斥；白名单显式声明
框架内置业务校验器删除影响存量用户升级破坏兼容先 Deprecated 保留一版 → 下版本移除；发布迁移脚本与文档

🎯 方案要点回顾

  1. 配置声明注解化：提取规则（@AiExtract）、枚举（@AiOptions）、通用校验（@AiRegex/@AiLength/...）、定制校验（@AiValid(by = 客户类)）、映射（@AiMapping）全部落在实体字段上，与代码同源。
  2. 校验职责分层：框架只留通用校验（非空/正则/长度/区间/枚举/确认）；一切业务化校验由客户自实现校验类承载，注解以 Class 参数引用，编译期可查、即插即用。
  3. 引擎零改动：新增 AnnotationAiTaskConfigService 作为配置源第二实现，复用现有提取/校验/标准化/映射/动作/状态机全链路。
  4. 平滑落地：config-source 三模切换 + taskType 白名单灰度 + 导出/对比工具 + 快速失败自检，迁移可回退、可度量。
