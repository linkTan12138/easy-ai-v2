1. 项目概览与技术栈

定位：企业客服自动化框架，以「智能入口」的形式接入对话，自动完成意图识别 → 场景匹配 → 参数收集 → 校验确认 → 业务动作执行的完整闭环。

两条并存链路：

  • 旧链路场景模板链路（AiServiceImpl + AbstractAiSceneProcessor）：配置存于 tb_task_field_template 表，字段收集逻辑在场景实现类中，校验通过 validField() 硬编码。
  • 新链路任务引擎链路（AiTaskEngine + AiTaskConfigService）：配置以 JSON 存于 ai_task_config 表，具备版本化（DRAFT → PUBLISHED → DISABLED）与任务绑定版本机制，是当前的主干演进方向。
维度技术选型
语言 / 框架Java 17，Spring Boot 3.4.x，以 Starter（easy-ai-starter）方式自动装配
ORMMyBatis-Plus 3.5.5（Mapper、分页、自动填充 MetaObjectHandler）
JSON / 工具Jackson（配置解析、状态持久化）、Hutool、Lombok
LLMDeepSeek / Doubao(火山方舟) / Kimi 三家 SDK 可切换（large-language-model.active），工厂模式 + Holder
数据库MySQL（配置表、会话任务表、会话记录表），Liquibase 管理变更集
工程结构3 模块：easy-ai-autoconfigure（核心）、easy-ai-starter（薄封装）、easy-ai-demo（演示）

4. 任务引擎核心流水线

DefaultAiTaskEngine.execute(taskType, taskId, userMessage, taskContext) 单轮处理流程：

单轮对话处理时序（状态机：INITIALIZED → COLLECTING → READY → EXECUTING → COMPLETED / FAILED）
用户消息
  │
  ▼
① 解析配置版本：已有任务绑定版本优先，否则取最新 PUBLISHED 版本
  │  （configService.get(taskType, configVersion)，DB JSON 反序列化为 AiTaskConfig）
  ▼
② 加载/创建 TaskState（任务状态，含各字段 FieldState）
  │
  ▼
③ FieldSelector.select()：筛选"待收集字段"
  │   过滤条件：未完成 + 前置条件(PremiseEngine)满足；按 order 升序
  │   若待收集为空 → 完成判定，进入动作执行
  ▼
④ ExtractionEngine.extract()：PromptBuilder 构建系统提示词（字段代码/名称/类型/
  │   说明/示例/规则/可选值 + 已收集上下文）→ LLM 调用 → 容错解析 JSON
  │   只保留 pending 字段结果，其余丢弃（不信任 LLM 输出）
  ▼
⑤ ValidationEngine.validate()：对每个提取字段执行校验器管道
  │   rawValue → V1 → V2 → ... → 标准值 + data 附加数据
  │   失败 → FieldState=INVALID(errorCode/errorMessage)，onFail=BLOCK 时整任务 FAILED
  ▼
⑥ NormalizationEngine.normalize()：对 VALID 字段执行标准化（如 PI966→完整描述）
  │   成功 → 替换 value + 合并 data；失败 → 置 INVALID 重新收集
  ▼
⑦ CompletionEngine.completed()：required 全部 VALID/CONFIRMED + 无 INVALID → READY
  │   未完成 → 生成"还缺什么"的追问文案（ResponseBuilder.buildNeedMore）
  ▼
⑧ MappingEngine.assemble()：按 MappingRule 将校验结果映射为动作参数
  │   表达式：$value / $rawValue / $data.xxx
  ▼
⑨ ActionEngine.execute()：执行 @AiAction 主动作 + @AiPostAction 后置动作
  │   成功 → COMPLETED；失败 → 回到 COLLECTING，保留进度重试
容错设计：整条管道被 try/catch 包裹，任何子引擎异常都不会击穿调用方对话流——降级为「需要更多信息」响应并持久化已取得的状态；状态先落库再返回，崩溃不丢失进度。

5. 配置模型（数据库 JSON）

ai_task_config.config_json 反序列化为 AiTaskConfig，结构如下（以 demo 的 ORDER_UPDATE 为例）：

AiTaskConfig 配置模型（FieldDefinition 是核心，覆盖"提取/前提/校验/标准化/映射"全生命周期）
AiTaskConfig                          # 一个业务场景配置（taskType + version 唯一）
├── taskType / version / name / description
├── fields: List<FieldDefinition>     # 字段定义列表（收集顺序 = order）
│   └── FieldDefinition
│       ├── code / name / type(STRING|INTEGER|...|STRING_LIST) 
│       ├── required / sensitive / order
│       ├── extraction: ExtractionConfig   # ★ 提取规则
│       │   ├── description    # 字段含义说明（进 Prompt）
│       │   ├── examples[]     # 示例值（进 Prompt）
│       │   ├── rules[]        # 提取约束（进 Prompt）
│       │   └── allowEmpty
│       ├── premise: PremiseConfig         # 前置条件（exists/eq/in + AND/OR 树）
│       ├── validation: ValidationConfig   # ★ 校验配置
│       │   ├── mode=PIPELINE / onFail=RETRY|BLOCK
│       │   └── validators[]: { type: "REGEX", params: {pattern, message} }
│       ├── normalization: NormalizationConfig  # 标准化 { type: "CARGO_DESC", params }
│       ├── mappings[]: MappingRule        # { target: "a.b", source: "$data.x" }
│       └── options[]: OptionDefinition    # 枚举 { label: "确认", value: 1 }
├── completion: CompletionConfig   # requiredFields / optionalFields
└── action: ActionConfig           # type: "UPDATE_ORDER", postActions: ["LOG"], params

配置生命周期：DRAFT（保存草稿）→ PUBLISHED（发布，同 taskType 旧发布版自动 DISABLED）→ DISABLED（停用）。新任务取最新 PUBLISHED；在途任务绑定创建时的版本，重发布不影响。

缓存策略：仅 PUBLISHED/DISABLED 的不可变快照进入 ConcurrentHashMap 缓存，以 taskType|version 为键；草稿不缓存。

6.2 现状痛点（本期改造的动因）

  1. 配置与代码分离：哪个字段用哪些校验器、参数是什么，全部写在 DB 的 JSON 里。新增/调整校验需改库（或通过管理接口），无编译期校验，JSON 手写易错、易产生脏配置。
  2. 字段语义不内聚：提取规则（description/examples/rules）、校验、枚举、映射散落在配置 JSON 与实体类两端，实体类本身没有任何标注，可读性差。
  3. 框架越权承载业务校验：CUSTOMER_EXIST、CHANNEL_EXIST 等明显是"客户业务侧"的校验逻辑，却以框架内置校验器形态打进 starter，每个接入方都要复用/扩展，框架日益臃肿且耦合具体业务。
  4. 旧链路 validField 硬编码：AbstractAiSceneProcessor.validField() 用 switch-case 按字段名校验，新增字段校验必须改基类子类的 Java 代码，复用性差。
  5. 定制校验门槛高：客户虽然可实现 FieldValidator + @AiValidator，但必须同时改 DB JSON 引用它，两步操作割裂，且缺少注解式声明入口。

7. 扩展点汇总

扩展点机制客户如何接入
场景处理器@AiScene(code) + 继承 AbstractAiSceneProcessor（旧链路）实现 transScenarioMsg / doProcess / validField
字段校验器FieldValidator + @AiValidator("TYPE")，启动时 ValidatorRegistrar 自动注册实现接口，配置 JSON 中按 type 引用
字段标准化器FieldNormalizer（Spring bean，按 type 查找）实现接口，配置 JSON normalization.type 引用
业务动作ActionExecutor + @AiAction("TYPE") / @AiPostAction实现 execute，配置 JSON action.type 引用
业务查询 SPICustomerLookupService / ChannelLookupService / CountryLookupService / WaybillLookupService实现 SPI 接口并注册 Spring bean
配置来源AiTaskConfigService 接口可替换实现（DB / JSON / 注解）
LLM 供应商LargeLanguageModel + 工厂新增 SDK 实现并注册工厂
观察：校验器 / 标准化器 / 动作 / SPI 均已做到"注册式扩展"，唯独配置声明（哪个字段用哪个扩展、参数是什么）仍是 DB JSON。注解化改造的实质就是把"配置声明"这一环搬到实体类上，与代码同源、编译期可查。

8. 架构结论

  • 骨架健康：引擎各阶段职责单一（extraction / validation / normalization / mapping / completion / action / state），接口 + 默认实现 + 注册表的结构清晰，扩展点丰富。
  • 演进方向明确：任务引擎链路（DB JSON 配置）已取代旧场景模板链路成为主干；但旧链路代码（AiService / AbstractAiSceneProcessor / 模板表）仍保留。
  • 改造切入点清晰：配置源抽象 AiTaskConfigService 是注解化的天然落点——新增注解扫描实现，引擎主体可零改动复用全部流水线能力（提取、校验、标准化、映射、动作、状态机）。
  • 待解决问题：①配置声明与代码分离；②业务校验器过度内置于框架；③实体类字段缺少语义标注。详见配套文档《注解化改造方案》。
